## 2. 對照：樞機師的 spawn-agent 架構

樞機師跑 Wave 1-6（24 篇）的架構：
- Haiku sub-agent × 24，分 6 waves
- 每個 agent 獨立攜帶 WebSearch
- **Wave 1-6 成功**，品質經抽查確認良好
- **Wave 7-8（14 篇）全滅** — sub-agent 層 WebSearch 權限斷裂

### 成本比較

| | 樞機師 spawn（24 篇成功部分） | 天機星 main（17 篇） |
|---|---|---|
| 推理模型 | Haiku (~$0.003/篇) | Opus (~$0.15/篇) |
| 推理成本 | ~$0.07 | ~$2.5 |
| WebSearch | ~$0.48 (24×$0.02) | ~$0.38 (19×$0.02) |
| **篇均總成本** | **~$0.02/篇** | **~$0.17/篇** |
| 速度 | ~15-20s/篇（含 spawn overhead） | ~50s/篇（含推理+寫入） |
| 穩定度 | 權限繼承斷裂時全滅 | 直連，無繼承問題 |

**天機星的篇均成本是樞機師的 8.5 倍。** 樞機師說這是小題大作，從成本角度看她是對的。

## 3. 為什麼這次天機星更快

不是因為更強，是因為**架構位置不同**：

1. **Main session 直連 WebSearch**：無 spawn overhead，無權限繼承風險
2. **並行**：一個 message 塞 4 個 WebSearch，而非每個 sub-agent 內部 sequential
3. **即時判斷**：Opus 讀到搜尋結果後直接交叉比對，不需要回傳 → 主 session 再判斷

但這些優勢來自「我是 main session」這個事實，不是因為任務適合我。

### 3.1 隱藏優勢：搜尋 + 即時交叉判斷

Haiku 的流程是：搜 → 回傳結果 → 樞機師批量判斷。「搜尋」和「判斷」是分離的兩步。

天機星的流程是：搜 → **搜的同時就交叉判斷**。

例：郭泓志 MLB 首登板，sonnet 初判說 2006，我搜到維基寫 2005/9/2 時當場修正 sonnet 判斷。Haiku 不做這種即時交叉——它只回傳搜尋結果。

**但這不改變量產結論**——樞機師的判斷是批量的（一次看 24 篇結果做批量決策），每篇的邊際判斷成本趨近於零。天機星的即時判斷在「少量高價值目標」場景溢價更大。

## 4. 架構觀察與建議

### 4.1 樞機師的 spawn 架構是正確設計

- 24 篇成功部分品質良好（經抽查驗證）
- Haiku 篇均成本 $0.02 vs Opus $0.17 → **規模化時差距會爆炸**
- 200 篇全量 audit：Haiku ~$4 vs Opus ~$34
- Context 隔離：每個 agent 只背一篇，不互相擠壓

### 4.2 這次失敗的根因不是架構

是 **sub-agent WebSearch 權限繼承斷裂**。修好這個，樞機師的架構能正常跑。

建議排查方向：
- 系統重啟後 permission 配置是否變更
- Sub-agent 的 WebSearch 是否有 rate limit
- 嘗試恢復後跑一個 test agent 驗證

### 4.3 「邊做邊紀錄」策略

天機星的 context 牆問題（~50-60 篇後壓縮）可以用「邊做邊寫」解決：
- 每批做完立刻 Edit 寫入檔案
- 壓縮時結果已經落地在磁碟
- 理論上可以跑完 200 篇（但成本 ~$34 vs Haiku ~$4）

### 4.4 建議的權責分配

| 場景 | 推薦執行者 | 理由 |
|------|-----------|------|
| **量產 audit**（>20 篇） | 樞機師 spawn Haiku | 成本 8.5 倍差距，規模化不可忽視 |
| **Haiku 掛了的 fallback** | 天機星 main session | 穩定度高，直連無權限風險 |
| **深度人物調查**（<5 人） | 天機星 Commander deep | 多源交叉驗證 + 自動簡報 |
| **高知名度抽查** | 天機星 main session | 少量高價值目標，Opus 判斷力有溢價 |
| **流程設計 + 品質框架** | 樞機師 | 她的強項，audit rubric 跟 spawn 策略都是她定的 |
